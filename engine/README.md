# The Discpress chdman engine

`engine/mame` holds **chdman from MAME 0.289** (tag `mame0289`, commit `f34f025`) and exactly the parts of MAME it links: 75 source files and the headers they include, listed in [`FILES`](FILES). It is a fork. Discpress builds it with [`wasm/Makefile`](../wasm/Makefile), for the browser (`build.sh`) and natively (`scripts/build-native.sh`), and nothing else from MAME is needed.

The paths mirror MAME's, so every file can be compared with its original. **[`mame-0.289.diff`](mame-0.289.diff)** lists every change the fork makes; Help → About shows it too. Current changes:

- **Browser build**, under `#ifdef __EMSCRIPTEN__`:
  - helper-worker hooks in `chd_file_compressor` (`chd.cpp`, `chd.h`);
  - `chd_file::wasm_read_ahead`, which reads a window of stored hunks in one go for `verify` and the extract commands, hands the compressed ones to helper workers, and lets `read_hunk` take them from memory (with the usual CRC check);
  - verify and extract read in 8 MB buffers instead of 32 MB;
  - compression and `read_ahead` also wait while results streamed into a folder are waiting to be written (`wasm_out_full`, `chdman.cpp`).
- **Resumable commands (`chdman.cpp`):**
  - The commands that compress (`createraw`, `createhd`, `createcd`, `createdvd`, `createld`, `copy`) and `compress_common` are C++20 coroutines (`chdman_task`). So are `verify`, `extractraw`, `extracthd`, `extractdvd` and `extractcd`, which pause while helpers decompress what they are about to read (`read_ahead`).
  - `main` is split into `chdman_start` (parse the command line) and `chdman_continue`.
  - In the browser, the page starts a command with `chdman_begin` and calls `chdman_resume` whenever the compression loop pauses to let helper workers' results arrive. This needs no Asyncify.
  - Natively nothing pauses and `main` runs each command straight through, with the same output, messages and exit codes as upstream.
- **`unicode.cpp`/`.h`:** the functions that needed utf8proc are removed; nothing in chdman used them.
- **Faster codec trials with the same output (`chdcodec.cpp`, `flac.cpp`, LZMA SDK `LzmaEnc.c`):**
  - For each hunk, the codec that won the previous hunk is tried first. Every other codec gets the best size so far as a limit and gives up as soon as its result can't win. As upstream, a codec listed earlier wins a tie, so the chosen codec and the compressed bytes don't change.
  - zlib, zstd and Huffman write into buffers only as large as a winning result. LZMA stops once its output passes that size (a check added to the SDK's encoder loop). FLAC stops after a block whose output passes it.
  - The generic `flac` codec keeps its big-endian encoding in its own buffer instead of encoding it a third time when it wins.
  - FLAC skips the MD5 of the audio when encoding to memory; the MD5 never reaches the CHD.
- **libFLAC's math (`window.c`, `lpc.c`, `fixed.c`):** `cosf` and `log` come from [`engine/libm`](libm/README.md), copies of glibc's algorithms, so CD audio encodes to the same bytes in the page as with chdman on Linux.
- **Faster hashing with the same results (`hashing.cpp`):** SHA-1 reads whole blocks as big-endian words and runs its 80 rounds unrolled. CRC-16 folds in eight bytes at a time (slice-by-8). In wasm, SHA-1 went from 120 to 650 MB/s and CRC-16 from 300 to 1,450 MB/s.
- **Faster ECC with the same results (`cdrom.cpp`, `cdrom.h`):** `ecc_verify` and `ecc_generate` compute P and Q for eight vectors at a time in 64-bit words, instead of a byte at a time from tables of offsets (removed): 3.4 times faster natively. The CD codecs verify every data sector's ECC once per codec they try, and extracting rebuilds it. Checked against an independent byte-at-a-time implementation on 200,000 sectors (all-zero, all-0xFF, random and damaged ones, every mode byte), and CHDs and extracted files equal 0.289's. The page's ECM decoder (`wasm/ecm.cpp`) uses it too.
- **Redump's layout for extracted CDs (`extractcd --redump`, `-rd`; `chdman.cpp`):** a `.cue` with CRLF line ends on any platform, and one `.bin` per track unless there is only one (then `<name>.bin`). That is how Redump's dumps are laid out, so a disc made from one comes back as the same files; the page extracts CDs this way by default. Without the option, output is upstream's.
- **Keeping the cue sheet (`createcd --keepcue`, `-kc`; `chdman.cpp`), opt-in:** the input `.cue` is stored as it is, as metadata (`CUES`) after the CD metadata and without the checksum flag, so neither SHA-1 changes and most readers ignore it; Kronos and Yabause (Saturn) and jgenesis (Sega CD) reject a CHD with any tag they don't know, so the page leaves `--keepcue` out for those consoles, and chdman 0.289 reads, verifies and extracts such CHDs as usual. `extractcd --redump` writes that sheet back, with the names of the files it writes, when those are laid out as the sheet's files (one `BINARY` file per track, or one for a single track); otherwise it writes its own. So what a CHD's tracks don't hold comes back: CATALOG, FLAGS, ISRC, INDEX 02 and later, `CDI/2352`. The CHD's bytes then differ from 0.289's (the plan's tier C), which is why it is off by default, in the page too.
- **The codec plan (`createcd`, `createdvd`, `createhd`, `createraw` with `--codecplan`, `-cp`; `chd.cpp`, `chd.h`, `chdcodec.cpp`, `chdman.cpp`), opt-in:** chdman tries every codec in the list on every hunk and keeps the smallest result, though most of them hardly ever win. With the plan, each hunk tries only the codecs meant for what it holds: a CD hunk in audio tracks `cdfl`, one in data tracks `cdlz` (`cdzl` wins about one data hunk in ten, by a few bytes), and a hunk of any other CHD every codec but `flac`. A CD hunk that holds both, or a codec list without those codecs, tries them all. The codec list in the header is unchanged, so every reader decodes the result, and the data and both SHA-1s are the same; the bytes differ where a codec left out would have won (the plan's tier C), so it is off by default. The choice depends only on where a hunk lies, so the CHD is the same at any thread count, and in the page (the codec slots travel with each hunk to the helper workers). Natively, `-np 4`, against the default: CD data 1.8 times less CPU and 0.22% larger, CD audio 1.9 times less and the same size, a mixed CD 2.0 times less and 0.11% larger, a DVD 1.4 times less and 0.06% larger (`docs/chd/measurements.md`).
- **libdeflate for the deflate codec (`--libdeflate`, `-ld` on the same four commands; `chd.h`, `chdcodec.cpp`, `chdman.cpp`), opt-in:** `chd_zlib_compressor`, which does `zlib`, `cdzl` and the subcode of `cdlz`, encodes with [libdeflate](libdeflate/README.md) at its level 9 instead of zlib's level 9: standard raw deflate that every reader decodes with zlib, so the checksums are the same, but not zlib's bytes (tier C). Natively, `-np 4`, CPU: with the default codecs 1.1–1.5 times less and a little smaller; with `-c cdzl,cdfl` (the page's "Faster to create") 1.5–1.8 times less and 0.3–0.7% smaller; with the codec plan on a DVD 1.17 times less than the plan alone, and smaller than chdman's default. Helper workers are told with the codecs (`wasm_par_enabled`'s flags).
- **Fixes to 0.289's failure handling and to the descriptors it reads wrong (`chdman.cpp`, `cdrom.cpp`, `cdrom.h`, `chd.cpp`, `chdcodec.cpp`, `huffman.cpp`, `avhuff.cpp`, `bitstream.h`, libFLAC's `lpc.c`, `fixed.c` and `stream_encoder.c`, LZMA SDK `LzmaEnc.c`); output for input that 0.289 reads right is unchanged, except the `.toc` that `extractcd` writes for a CD with a pregap it holds, and the GD-ROM outputs below that 0.289 can't read back:**
  - `verify` exits 1 when the data doesn't match the header's SHA-1, unless `--fix` corrects it. Upstream exits 0, so scripts and the page reported success.
  - An output is never written over an input: `copy -i x -o x -f` used to truncate `x` and then delete it.
  - `extractcd` of a CHD that isn't a CD, and a unit or sector size of 0, are errors (exit 1). Upstream aborts on `throw nullptr` or divides by zero.
  - A failed or short read of the input of `createraw`, `createhd` or `createdvd` is an error (exit 1). Upstream ignores it, compresses whatever its buffer holds and exits 0, so the CHD silently holds the wrong data; for an unreadable input it can't even open the result.
  - Cue sheets it read wrong, silently: audio in a `MOTOROLA` (big-endian) file was byte-swapped anyway, and so was a data track that opens one; a file with several tracks after another file was read at offsets carried over from the first file; the last of several tracks in a file that another file follows got the whole file; a `.wav` with several tracks gave the first track all of it. Each now gives the CHD of the same disc laid out plainly, one file per track. 5,676 real Redump cue sheets give upstream's CHDs byte for byte.
  - A cue sheet in EAC's "gaps appended to the previous track" layout (a track's `INDEX 00` at the end of one `FILE`, its `INDEX 01` in the next) gives the CHD of the same disc as one file with `INDEX 00`/`INDEX 01`: the pregap is read from the end of the first file (a track in two pieces, `track_input_entry::pieces`, which the CHD writer in `chdman.cpp` reads in order) and the track before it ends there. Upstream read the track from the first file at the second file's `INDEX` points (`PREGAP:-300`). EAC's other layouts (gaps left out, as `PREGAP`; gaps appended to the next track) are upstream's.
  - Nero images (`parse_nero`): each track starts at its `INDEX 00` in the image, and the pregap the image holds (`INDEX 00` to `INDEX 01`) is stored, flagged `PGTYPE:V…`, as for a cue sheet's `INDEX 00` in the same file, so an NRG gives the CHD of the equivalent single-file cue sheet. Upstream added up the earlier tracks' lengths without their pregaps (the wrong bytes after a track whose pregap the image holds) and dropped the pregap's data, making it a virtual pregap. An image without pregaps gives upstream's CHD; one whose tracks have pregaps (the `ps1-nrg` fixture's audio track, most real images) does not. A track outside the file is an error, and so is a sector size other than the track mode's (2048 bytes for mode `0x0000`, 2352 for `0x0600` and `0x0700`): upstream read that many bytes into each frame of 2448, a heap overflow past 2448 and a CHD of other data below (exit 0).
  - cdrdao TOCs (`parse_toc`) are read as cdrdao reads them: `DATAFILE "f" [#offset] [length]`, `AUDIOFILE`/`FILE "f" [SWAP] [#offset] start [length]` (a time is `MM:SS:FF`, or a number of bytes for `DATAFILE` and `ZERO`, of samples for `AUDIOFILE` and `SILENCE`), and without a length the rest of the file. Several file statements in a track are read in order (runs of one file that follow each other are one; others make a track in pieces), and `ZERO`/`SILENCE` are zeros no file holds. `START` marks `INDEX 01`: frames before it that the track holds are a stored pregap (as a cue sheet's `INDEX 00`), zeros before it that no file holds (`ZERO`, `SILENCE`, or `PREGAP`, which is silence and `START`) a virtual one (as a cue sheet's `PREGAP`); `START` alone is where the statements so far end. An audio file whose name ends in `.wav` is a WAVE file, as in cdrdao (`TrackData.cc`): its `#offset` is where the WAVE file starts in the file (its header is read there), start and length count from its samples, which are little-endian (`SWAP` means big-endian), and they end with its data chunk or the file, whichever comes first; so it reads as a cue sheet's `WAVE` file. A length of 0 is the rest of the file, as no length (cdrdao's `determineLength`), and the rest of an audio file is whole samples. A statement that asks for more than its file holds is an error when the TOC is read, as in cdrdao (upstream failed reading), and so are numbers past 2^40 bytes (the engine before wrapped them), samples (`AUDIOFILE`, `FILE`, `SILENCE`) in a track with sub-channel data (cdrdao refuses them; they were sized as bytes of frames that have it), and a `ZERO` whose mode or sub-channel mode isn't the track's (cdrdao makes sectors of that mode, which a CHD track can't hold). A track whose data ends inside a sector (a file or a length that isn't a whole number of sectors) is padded to the sector with zeros, as cdrdao does; data after such a statement in the same track would not start on a sector and is an error. Each form gives the CHD of the equivalent cue sheet. Upstream made `START` a virtual pregap though the file holds it (so the `ps1-toc` fixture's CHD changes: its audio track's pregap is now stored, as in `mgs disc1.cue`), ignored `PREGAP`, `ZERO` and `SILENCE`, kept a track's last file statement only, read a lone `DATAFILE` length after track 1 as an offset (the TOCs `extractcd -sb` writes lost every track after the first), a lone `AUDIOFILE` start on track 1 as a length, a plain number as frames, gave a statement without a length no data, read a `.wav` raw (the header as audio, the samples byte-swapped) and dropped a last partial sector. A cue sheet's last partial sector is still dropped, as upstream does (Redump's files are whole sectors). The TOCs `extractcd` writes read as before (with `#0` for `-sb`, which upstream needs), and so does any TOC upstream read right. A track without data, a `START` at or past a track's end, and samples in both byte orders in one track are errors.
  - `extractcd` to a `.toc` writes a pregap the CHD holds (a cue sheet's `INDEX 00`, `PGTYPE:V…`) as what it is, frames of the track's file before `START`. Upstream wrote `ZERO` before it too, which reads back (in cdrdao, in the engine and, as a virtual pregap, in upstream) as that many more frames of zeros: CHD → TOC → CHD made a longer disc. So `.toc` output differs from upstream's by that one line for each track with a stored pregap (among the fixtures `mgs disc1`, `ax101`, `codec mix cd`, `fidelity`, `moto`, `shared`, `wavs`, `bench-cd`, `ps1-toc` and `ps1-nrg`); a pregap that isn't in the CHD (a cue sheet's `PREGAP`) is still `ZERO` and `START`, and the track files are upstream's. Every CD fixture now makes the same CHD, byte for byte, after `extractcd` to `.toc` (with or without `-sb`) and `createcd` from it.
  - GD-ROMs read back from every format `extractcd` writes for them. A TOC can't describe one (it has no high-density area, and the padding before LBA 45000 is in no file), so `extractcd` refuses `.toc` output for a GD-ROM; upstream wrote lengths the files don't hold, which read back as an error (or from `-sb` as a CD of other data). The `.cue` of a CHD made from a GDI has a `PREGAP` where the GDI leaves a gap out of every file (track 2's), and `createcd` now reads a GD-ROM cue sheet's `PREGAP` as zeros padding the track before, as the GDI's gap is: the same CHD, byte for byte. Upstream took that pregap from the start of the track's file, which then lacked as many frames at its end: a read error, or the track's data moved. For a disc whose last data track follows audio ("type 3 split"), `extractcd` keeps the 75 frames of that track's pregap that TOSEC's GDI has at the end of the audio track in the audio track's file, and writes the 150 in no file as the `PREGAP` (upstream left the 75 out of every file, and wrote `PREGAP 00:03:00`); for two data tracks ("type 3") it moves the 225 frames only when the track before holds them and has no padding. `--redump` writes Redump's layout whatever the CHD was made from, each track's pregap at the start of its own file (from a GDI's CHD, its padding): the files of the Redump dump, and a CHD with the same data (the one the Redump sheet makes; a GDI's CHD keeps its gaps as padding, so its SHA-1 differs). `.gdi` output and the `.cue` of a CHD made from a Redump sheet are upstream's. A cue sheet with a stored pregap longer than its track is an error.
  - Cue sheets (`parse_cue`): a track's `INDEX` points must be in order and not go back in the same file, a track in the same file as the next must end before the next starts, and every track must have frames from its `INDEX 01` on. Upstream made negative pregaps or lengths of them (exit 0, or a read error), and tracks of their pregap alone, whose `.toc` doesn't read back.
  - `cdrom_file`'s logical reads (`read_data` and `read_subcode` without `phys`, `get_track`), which no chdman command uses but the page's identification does (`wasm_probe_read`): a track's LBAs start at its `INDEX 00`, so a pregap the CHD holds is read from the track's own data, and a pregap or postgap it doesn't hold (or a gap between sessions of a mounted image) reads as zeros. Upstream counted a track's pregap as the track before's, so it read that track's padding and then data shifted by it, and for a gap the CHD doesn't hold the next track's data. LBAs from `INDEX 01` on, which is all the page reads, are read as before. `tests/support/cdprobe.cpp` (`make -C wasm T=native cdprobe`) reads every LBA as the page does.
  - libFLAC's LPC and fixed-predictor restores (`lpc.c`, `FLAC__lpc_restore_signal`; `fixed.c`, `FLAC__fixed_restore_signal`) compute in unsigned 32-bit arithmetic: on damaged `cdfl` data its signed sums and products overflowed, which C leaves undefined (UBSan flags it). The build wrapped them as two's complement, and unsigned arithmetic gives the same bits, so decoding is unchanged (each checked against the old function, built with `-fwrapv`, on 200,000 random blocks with gcc and clang); the encoder never calls them.
  - Undefined behavior UBSan reports, with the same results: the LZMA encoder stored its properties' dictionary size (`LzmaEnc_WriteProperties`, `LzmaEnc.c`) through a `UInt32` pointer at an odd address, now with `memcpy`; the zlib and LZMA allocators (`chdcodec.cpp`) kept each block's size in 4 bytes in front of it, so every block, the codecs' state structures among them, was only 4-byte aligned, and now keep it in 16 (`alignof(std::max_align_t)`); `msf_to_frames` (`cdrom.cpp`) overflowed an `int` on huge minutes, and now clamps (the same results for any time that fits); the bit writer (`bitstream.h`) shifted a 32-bit value by 32 when writing no bits (as for a map without copies of hunks), and now returns, as it did after the shift; libFLAC's encoder (`stream_encoder.c`) added an offset to a null pointer when it doesn't use escape codes, and now passes the null pointer; a map or metadata of 0 bytes took element 0 of an empty vector (`chd.cpp`), now `data()`.
  - Memory that LeakSanitizer reports: the command line's option values (`chdman_run`), `extractcd`'s `cdrom_file`, and after an error, the compression work items still out (`~chd_file_compressor`). Other allocations on the error paths are freed as `report_error` unwinds, and descriptor parsers that return early without closing their file (upstream's) are left as they are: each runs once per command.
  - `cdrom_file::get_track_index` (not used by chdman or the page) gives 0 for a frame in a track's pregap: since `logical_to_chd_lba` gives the pregap to its own track (above), counting back from `INDEX 01` there wrapped.
  - An `.iso` of 2352-byte sectors (`parse_iso`) is typed by its first two sectors' sync pattern and mode byte as well as its size: upstream typed it by size alone, so an image of 128·n sectors (also a multiple of 2048 bytes) came out as 2048-byte `MODE1` sectors, and one of 146·n (a multiple of 2336) as 2336-byte `MODE2`. Such an image now gives `MODE2_RAW`, as upstream types every other image of 2352-byte sectors; images of 2048- and 2336-byte sectors are upstream's.
  - `extractdvd` of a CD or GD-ROM CHD is an error (exit 1): upstream wrote its frames, subcode and all, as an `.iso`. `extractraw` still writes them.
  - A descriptor with no tracks, tracks without data (a cdrdao TOC track whose statements hold nothing) or track numbers outside 1–99 is an error (exit 1). Upstream spins forever, aborts or segfaults.
  - So are cue or cdrdao TOC lines that belong to a track (`INDEX`, `PREGAP`, `FLAGS`, `DATAFILE`, `START`…) before the first `TRACK`, which upstream writes before its track table; a GDI track file that is missing or empty, or a GDI audio track of size 0 (upstream makes an empty track and exits 0, or divides by zero); and an NRG image with a first track of 0, a sector size of 0, or a chain of chunks without `END!` (upstream writes before its track table, divides by zero or loops forever).
  - `createcd` never writes over a track file the descriptor names (upstream truncates it, then deletes it).
  - `extractcd` of a CHD with a damaged hunk is an error, as with the other extract commands. Upstream writes whatever it last read and exits 0.
  - A FLAC stream that ends before its hunk is complete (damaged `flac` or `cdfl` data) is a decompression error: upstream's decoder asks for more forever (`flac.cpp`).
  - A hunk stored as a copy of another hunk of the same file is followed in a loop, to the hunk that holds the data, and a chain that leads back to itself is an error (`self_target`, `chd.cpp`). Upstream calls `read_hunk` again for each step, so a map that makes a hunk a copy of itself, as a damaged or crafted file can, overflows the stack. Copies of copies that end are read as before.
  - A hunk whose stored length is larger than a hunk is an error (`read_hunk`, `codec_process_hunk`): upstream reads that many bytes into its hunk-sized buffer. So is a hunk compressed with a codec the CHD has none for (a v3/v4 CHD without compression whose map says a hunk is compressed, a v5 map naming an empty codec slot), and a hunk in a parent in a CHD that has none: upstream calls through a null pointer.
  - A CHD of a hunk or three can be read: upstream sizes the map's buffer without the Huffman tree that opens it, so the map overflows and is cut short, and the CHD it made (exit 0) fails with "Decompression error" (`compress_v5_map`, `chd.cpp`). Where upstream's map fits, which is every CHD of more than a few hunks, the bytes are the same.
  - The CD codecs compress the subcode into what is left of the hunk-sized buffer; upstream lets it run past the end when the sectors hardly compress (a heap overflow). Such a result is too large to win either way, so the CHD is the same (`chdcodec.cpp`).
  - `dumpmeta` without `-o` prints its banner on stderr, so stdout carries only the metadata.
  - A header with a hunk or unit size of 0, or a logical size of more hunks than a map can count (2^32), is an error ("Invalid file"), and so is a map whose size in memory doesn't fit in 32 bits (`check_sizes`, `create_open_common`, `chd.cpp`). Upstream divides by zero, or computes the size in 32 bits and makes a map too small for its hunks, then reads and writes past its end (a segfault at 358 million hunks).
  - A map that would run past the end of the file is the error reading it gives ("Input/output error") before its buffer is allocated: upstream allocated what the header said, up to 4 GB, first (`past_end`, `chd.cpp`).
  - The Huffman lookup table's entries that no code covers (only a damaged tree leaves any) decode as code 0 of no bits (`build_lookup_table`, `huffman.cpp`): upstream never set them, so decoding took bit counts from whatever that memory held.
  - A Huffman tree with more codes than one bit has room for (a damaged `huff` hunk, LaserDisc audio, or a v5 map's tree) is a decompression error (`assign_canonical_codes`, `huffman.cpp`): upstream gave codes more bits than their length and wrote the lookup table past its end, on the stack for a map or a `huff` hunk ("stack smashing detected").
  - A CD codec's hunk (`cdlz`, `cdzl`, `cdzs`) whose header is longer than the hunk's data, or says its sector data is, is a decompression error (`chdcodec.cpp`): upstream decoded past the end of the data, and the subcode's length wrapped around. So is a v5 map that reads more than 32 bits at a time (`decompress_v5_map`): upstream's bit reader shifted by a negative count. A field of exactly 32 bits is read as such (`bitstream_in::remove` empties the buffer): upstream shifted the buffer by 32, which C++ leaves undefined, and in practice kept its bits, so the next field was read with them.
  - CD track metadata is read with a width for each string (`%15s`, the longest a CD has being 15 characters): upstream's `%s` wrote a longer one past the end of its 16-byte buffer, on the stack (`parse_metadata`, `cdrom.cpp`).
  - CD metadata that leaves out a track (a track number repeated or skipped), and old-style binary CD metadata (`CHCD`) shorter than its table, with more than 99 tracks or with sectors no CD has, are invalid data (`parse_metadata`, `cdrom.cpp`): upstream made a track of 0-byte sectors, which `extractcd` divided by, or read past the end of the metadata and of a sector's buffer.
  - Reading or writing 0 bytes (`read_bytes`, `write_bytes`) does nothing: upstream's last hunk wrapped around at offset 0, and it read a whole hunk into the caller's buffer. The page's identification reads a CD track that has no metadata (a damaged CHD's) that way.
  - LaserDisc (`avhu`) hunks: a frame larger than the hunk, more than 16 audio channels, or raw audio shorter than its samples is a decompression error (`chdcodec.cpp`, `avhuff.cpp`). Upstream decoded past the end of the hunk, of its tables of channels, and of the data.
  - Any other unexpected exception is an error instead of a crash.
  - `tests/fuzz/` fuzzes the engine (libFuzzer, ASan and UBSan; `scripts/fuzz.sh`, `.github/workflows/fuzz.yml`), and found the faults above in maps, Huffman trees and the CD and LaserDisc codecs (the map size in 32 bits while looking at one), and the undefined behavior below.
  - `tests/ui/engine.spec.js` compares each of these with upstream.

## Rules

- **CHDs stay identical to chdman 0.289's.** Unless a change is an explicit, opt-in output tier (see [`docs/chd/fork-plan.md`](../docs/chd/fork-plan.md)), the default output must stay byte-identical to unmodified chdman 0.289. The tests check it against `build/chdman-0.289`, which `scripts/build-upstream.sh` builds from the MAME release with the same compiler flags.
- **`engine/mame` only holds files that come from MAME.** Change them in place, keep MAME's paths, and run `scripts/engine-diff.sh` to refresh `mame-0.289.diff` (`--check` only verifies it). New code goes elsewhere, like the browser glue in [`wasm/`](../wasm).
- **Moving to a newer MAME release:** fetch it (`scripts/fetch-mame.sh`, after changing its commit), apply `mame-0.289.diff` to the new files, copy them over, and check the output against the new upstream build.
